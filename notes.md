# Event operations

- Event date, venue, judging timings, and badge dimensions live in `src/eventDetails.js` so public and organizer views stay in sync.
- Set `ORGANIZER_PASSWORD_HASH` in the local environment and Render before using `/organizer`. Generate a salted hash locally with `npm run organizer:hash-password`; never store the plaintext password in the repository. Changing the hash invalidates existing organizer sessions.
- Accept applicants with `npm run applicants -- list` (who hasn't been emailed yet; `--all` shows everyone), then `npm run applicants -- accept <id>...` with the IDs you chose (there is deliberately no "accept everyone" option). Without `--send` it is a dry run that changes nothing and saves an email preview to `prints/`. With `--send` (and `BREVO_API_KEY` and `EMAIL_FROM` in the local `.env`) it asks for confirmation, marks them accepted, and emails each one through Brevo, recording `acceptance_email_sent_at`; re-running skips anyone already emailed. Brevo cannot recognize a repeated send, so each attempt is recorded first: if Brevo gives no clear answer, that applicant is flagged "Unconfirmed" and skipped by later runs until you check Brevo's transactional log (tag `acceptance`) and run `npm run applicants -- mark-sent <id>` (it was delivered) or `retry <id>` (it was not). It refuses to accept anyone after `rsvpDeadline`, and to send before the latest update is deployed. Brevo's free plan sends 300 emails a day, sign-up emails included; if the limit is hit, run the same command again the next day. `printed` defaults to `FALSE`, and `meal_count` to `0`.
- Before a run, the command shows how many emails Brevo can still send today. The site's own emails (verification, receipts, password resets) stop at 150 per 24 hours, logged in `email_sends`, so the rest of Brevo's 300 a day stays free for acceptances. Large batches are best sent after applications close. `mark-sent` and `retry` take the same lock as a send, and `retry` waits until an attempt is 15 minutes old.
- New applications close at `applicationsCloseAt` in `src/eventDetails.js` (end of November 8, Toronto time). After that, sign-up still works, but the dashboard's Apply button is greyed out, `/apply` shows "Applications closed", and the API refuses new applications. Existing applicants are unaffected.
- Late applicants the organizers approve are listed in `LATE_APPLICANT_HASHES` in `server/index.js`, as the SHA-256 of their canonical email: lowercase, and for Gmail without dots or a `+tag` (so the address stays out of this public repo and matches however they spell it; make one with `node --input-type=module -e "import { canonicalEmail } from './server/eventOperations.js'; import { createHash } from 'node:crypto'; console.log(createHash('sha256').update(canonicalEmail('name@example.com')).digest('hex'))"`). They can still apply after the deadline, are accepted the moment they submit, and get the normal acceptance email right away instead of a receipt. It is recorded like an `applicants` send, so `npm run applicants -- list` shows whether it went out, and an unconfirmed one is handled with `mark-sent` or `retry` as usual.
- After the RSVP deadline, or after a waiver reset, hackers can't RSVP themselves: once their waiver is in, a lead organizer runs `npm run waivers -- confirm-rsvp <id>`.
- Meal scans need an accepted, RSVP'd hacker. A second scan of the same badge within `mealScanCooldownMinutes` (180, so one lunch can't count twice) shows "Already recorded" and isn't counted, so rescanning after a dropped connection is safe.
- Accepted hackers upload their signed waiver (PDF, JPG, or PNG; up to 4 files of 5 MB each; photos are shrunk in the browser) from the dashboard. Submitting it unlocks the RSVP button, which closes at `EVENT_DETAILS.rsvpDeadline`. The participant pass (meal QR) and badge printing are only for hackers who have RSVP'd. Files are stored in the `waiver_files` table, can't be opened on the website at all (the organizer password is shared with meal-scan volunteers). Lead organizers with the database login check them with `npm run waivers -- list` and `npm run waivers -- download <id>...` (or `--submitted`), which saves them to DownloadsONHacks waivers, outside this OneDrive folder; delete them after checking. `/organizer` shows only the overall counts; per-hacker waiver status, resets (`npm run waivers -- reset <id>`), and RSVP confirmations (`confirm-rsvp`) are command-line only, and are deleted automatically `waiverRetentionDays` after upload. Resetting a waiver (`npm run waivers -- reset <id>`) deletes its files and the RSVP so the hacker can upload again.
- `/organizer` scans meal QRs, imports a full Devpost Projects data CSV, and assigns projects once. Include personally identifiable information so team emails can be matched to accepted applications. Emails match ignoring case, and Gmail addresses also match when only dots, a `+tag` or `googlemail.com` differ (they reach the same inbox); other providers need the exact address. Only `Submitted` projects are imported; drafts are skipped. Re-imports replace the previous roster, so correct mismatched emails in the CSV and re-import before locking assignments.
- Judges use `/judges`, a separate black-and-white panel. They sign in with their first and last name (ratings are kept per name, so two judges must not use the same name) and the shared judge password. The password is stored only as a scrypt hash in the database's `app_settings` table, never in this public repository; set or change it with `npm run judges:set-password` (it uses the `DATABASE_URL` in the local `.env`). Changing it signs every judge out within 30 seconds. Importing the Devpost CSV on `/organizer` fills the panel with every submitted project, including its description, team names, built-with tags, demo and try-it links, and opt-in prizes. Each judge rates each project 1-5 and can add a comment; both save as they go. Ratings are keyed by the project's Devpost URL, so re-importing keeps them. Every rating and comment is saved and returned, ranked by average, by `GET /api/organizer/judging-results` (organizer session required); the `/organizer` page no longer shows them. On `/judges`, the Rated tab lists that judge's own ratings from highest to lowest.
- The October 18 Devpost CSV in the repository root contains synthetic QA projects, not real submissions. Never import it into production; replace it with a fresh Devpost export after submissions close. Project exports named `projects-*-with-pii-*.csv` are ignored by Git.
- Assignment previews default to two rooms (Room 1 and Room 2) and 17:30-20:00, matching the schedule; change `defaultJudgingRooms`, `defaultJudgingStart`, or `judgingWindowMinutes` in `src/eventDetails.js` if it moves. Each project gets five minutes to pitch plus one minute for changeover. Room count and start time can be changed until the one-time assignment is confirmed; overtime requires explicit confirmation. Every submitted project gets a slot; projects with unmatched or duplicate team members need a "Schedule them anyway" confirmation, and those hackers won't see their time on their pass. Imports are blocked after assignments are locked.
- Run `npm run badges:generate` locally for Letter sheets, `npm run badges:generate -- tabloid` for Tabloid sheets, or `npm run badges:generate -- a4` for A4 sheets (landscape, two badges per sheet, because portrait A4 is too narrow for two 4-inch badges). Set a reachable `DATABASE_URL` in the local `.env` first. The command exports badges for confirmed (RSVP'd), unprinted participants with `lanyard_design.png` into the git-ignored `prints/` folder. Letter holds two 4x6-inch badges per sheet; Tabloid holds four, with a 0.125-inch gutter. It marks only those applications `printed = TRUE` after the PDF is safely written to disk. Reset `printed` to `FALSE` in PostgreSQL for a replacement badge. Print at actual size, not "fit to page."
- The same opaque QR value appears on the badge and `/participant`. Only an authenticated organizer scan can increment the meal count.
- Participant names are capitalized for display on badges, passes, meal scans, and the dashboard; original application names remain unchanged in PostgreSQL.
- Badge names use bundled Noto fonts for East Asian, Korean, Arabic, Devanagari, and Hebrew scripts, including mixed-script names. Their SIL OFL license files are in `public/fonts/`. The participant pass refreshes while visible, clears after access is revoked, and can also be refreshed manually.
- The app no longer uses the legacy `event_applications.status` field. Existing databases may still have it; inspect production values and external queries before dropping that column. Keep the `/login` and `/register` redirects, existing-database migrations, and Google-account repair until their compatibility needs are verified.
- Hackers who forget their password use "Forgot password?" on the sign-in page: a link to `/reset-password` is emailed, expires in 1 hour, and signs them in after they choose a new password (it also verifies an unverified account).
- Waiver deletion runs when the server starts and every 12 hours while it is awake. The free Render plan sleeps when idle, so `.github/workflows/daily-wake.yml` wakes the site once a day. Before suspending or deleting the web service, run `DELETE FROM waiver_files WHERE uploaded_at < NOW() - INTERVAL '45 days';` (and delete any remaining waivers once they are no longer needed).
- Private pages (`/organizer`, `/judges`, `/dashboard`, `/participant`, `/apply`, `/verify-email`, `/reset-password`) are excluded from search engines by `public/robots.txt` and an `X-Robots-Tag: noindex` header.
